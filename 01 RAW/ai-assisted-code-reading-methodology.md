# AI 辅助代码阅读方法论：让人掌握代码并理解代码

研究日期：2026-08-24  
研究目标：寻找可以让人保持代码掌握权的 AI 辅助阅读方法。这里的“完全掌握”采用可验收的定义：人能够用自己的话说明目标与边界，追踪关键控制流和数据流，预测正常、边界与失败行为，指出证据位置，运行验证，并能在需要修改时解释每一处改动的理由与影响。

## 一、研究范围与判断方式

本次检索优先选择四类来源：

1. 程序理解与调试领域的原始实验、田野研究和同行评审论文。
2. 认知学习与代码教学中的原始实验。
3. LLM 辅助编程、代码理解和开发者行为的原始用户研究。
4. GitHub、Microsoft 等产品方关于 AI 输出验证的官方文档。此类文档用于说明工具边界和操作要求，不把产品方的建议当作独立的效果证明。

文中的判断分为三层：

1. **来源直接支持**：来源明确报告了研究对象、方法和结果。
2. **跨来源归纳**：多个来源指向同一实践方向，文中会说明依据。
3. **实践建议**：结合来源设计出的工作流，适合试用和验收，不能直接视为已经完成实证验证。

## 二、核心结论

### 1. 人的理解结果要落在自己的模型、预测和证据上

经典程序理解研究把阅读描述为从问题域、任务目标、程序结构到运行行为的知识重建过程。Brooks 的模型强调由较宽的假设开始，再根据程序文本和文档逐步细化。Pennington 的实验显示，专业程序员早期更容易按程序执行片段和控制流组织理解，任务目标会在后续理解中发挥更大作用。

由此得到的实践要求是：AI 可以帮忙找入口、列候选路径、解释局部语句和提出假设，人需要自己维护一份会随证据更新的理解记录。只阅读 AI 的长篇总结，无法证明已经获得了可操作的程序模型。

### 2. AI 适合做候选解释、问题生成和假设搜索

对 Copilot 使用行为的研究把交互分为两种模式。加速模式中，程序员已经知道下一步要做什么，工具帮助减少输入。探索模式中，程序员还在寻找 API、算法或实现路径，需要更慢的提示、比较和验证。探索模式通常伴随更仔细的代码检查、执行、静态分析和文档查阅。

这说明阅读任务应明确标记当前模式。熟悉的小片段可以让 AI 提速。遇到陌生代码、隐含状态、外部副作用和安全边界时，应切换到探索模式，要求 AI 提供候选假设与验证步骤，保留人的判断环节。

### 3. 阅读要形成“预测、执行、对照、修正”循环

专业开发者研究中反复出现复现、定位、检查、模拟、上下文化等活动。调试研究还显示，开发者会在导航、编辑、测试、检查程序状态和查阅外部资料之间切换。正确假设较早出现时，后续修复成功率更高；只给出可疑位置，对形成正确假设的帮助有限，提供可检验的候选假设更有价值。

因此，AI 的最佳介入点是帮助整理候选假设、给出区分假设的输入和观测点。最终结论要来自源代码、测试、调试器、日志、静态分析或官方文档等证据。

### 4. 自我解释和主动回忆比重复阅读更适合作为掌握检查

Chi、Bassok、Lewis、Reimann 和 Glaser 的研究发现，理解较好的学习者会生成更多自我解释，把步骤和原理联系起来，并持续监测自己是否理解。代码教育中的随机对照研究也观察到，要求学习者解释代码并接受问题式提示，有助于代码输出预测和概念学习。Roediger 与 Karpicke 的实验显示，延迟测试中，主动回忆比重复阅读带来更好的保持效果。

实践中应让人先合上 AI 输出，用自己的话写出解释、伪代码、状态表和待验证问题，再让 AI 做批评。AI 可以充当教练，不能代替回忆活动本身。

### 5. 通过测试不等于已经理解

测试能证明某些输入下的行为符合预期。它无法单独证明人理解了所有分支、异常、并发、资源生命周期、配置来源和外部副作用。LLM 生成的代码还可能让初学者出现自动化偏差和过度自信。2025 年一项针对 32 名 CS1 学生、160 个任务实例的研究报告了较低的单任务成功率，并指出 Python 语法陌生、英语理解障碍和自动化偏差等问题。

验收必须同时包含人的复述、反例预测、运行证据和改动解释。

## 四、推荐工作流：人主导，AI 辅助，证据闭环

### 阶段 0：先定义阅读目标

人的动作：写下本次需要回答的问题，例如“请求从入口到数据库写入经过哪些模块”“这个状态何时进入恢复分支”“修改这一行会影响哪些外部行为”。同时写出当前已知事实、初始假设和未知问题。

AI 的职责：把目标改写成可检查的问题清单，帮助列出候选入口、相关符号和可能的运行路径。AI 必须把内容分为“代码或文档直接显示”“根据上下文推断”“仍需验证”。

验收：阅读开始前，人能用几句话说出范围、入口、预期输出和不在范围内的内容。

### 阶段 1：建立代码库地图

人的动作：确认构建方式、测试入口、运行命令、配置来源、外部依赖和部署边界。选择一个具体的垂直切片，形式为“输入或事件 → 入口 → 关键转换 → 状态变化 → 输出或副作用”。

AI 的职责：根据给定目录、文件和符号生成候选地图，指出每条关系对应的文件位置。AI 不应把没有看到的文件、接口或运行结果补写成事实。

验收证据：入口函数、调用点、配置项、测试或复现命令都有可点击的源文件位置，地图中标出未知关系。

### 阶段 2：按执行片段追踪控制流和数据流

人的动作：每次只读一个可管理的代码单元。先说明控制流，再追踪输入如何变成局部变量、返回值、消息、文件或数据库操作。遇到关键分支，写出进入条件、跳过条件和异常路径。

AI 的职责：对当前片段提出逐步问题，生成调用链候选，解释术语和 API，并提醒可能遗漏的分支。AI 输出每项都要附 `文件:行号` 或相关官方文档。

验收证据：至少完成一次人工状态表，记录输入、变量、分支条件和输出。对重要函数能回答“调用它之前需要什么”“调用它之后改变了什么”。

### 阶段 3：先预测，再运行

人的动作：在运行测试或调试器前，先写出预测结果。至少准备一个正常输入、一个边界输入和一个失败输入。记录预期的关键状态变化，再运行测试、REPL、日志或调试器进行比较。

AI 的职责：帮助产生边界案例和互相竞争的解释，给出每个解释能被什么观测区分。AI 可以建议断点、日志点和测试输入，不能替人宣布假设成立。

验收证据：每个已接受结论至少有一条代码证据和一条行为证据。预测失败时更新理解记录，并说明更新原因。

### 阶段 4：进行自我解释与主动回忆

人的动作：暂时关闭 AI 输出，用自己的话完成以下四项：

1. 用三到十句话说明这段代码解决的任务。
2. 用伪代码重写主要步骤。
3. 画出一个关键输入的控制流和数据流。
4. 写出两个仍然不确定的问题及其验证方式。

AI 的职责：在人完成初稿后，逐条检查是否有代码证据，提出一个问题帮助人发现遗漏，比较人的解释与实际执行结果。AI 先做检查，再给出补充说明。

验收：人能在没有 AI 输出的情况下复述这段代码，并能回答“如果删除这一步会发生什么”“哪个输入会走另一条路径”。

### 阶段 5：用对抗问题检查理解

人的动作：主动寻找与当前解释冲突的代码、注释、测试、配置和运行结果。关注命名与实际行为不一致、默认值、异常处理、并发时序、缓存、权限、资源释放和外部 API 约束。

AI 的职责：扮演审查者，提出反例、遗漏分支和替代解释。每个问题都要说明依据。对没有依据的怀疑标记为待验证。

验收：对每个高风险假设都有一个反例或验证结果。未解决的问题进入待办表，不能写成确定结论。

### 阶段 6：在理解之后再修改

人的动作：先写变更目的、保持不变的行为、验收条件和回滚方式。要求 AI 先给出多个方案和风险，再决定是否让它生成补丁。逐段阅读 diff，说明每个修改的目的、影响和测试覆盖。

AI 的职责：生成小范围候选 diff，标记涉及的调用方、状态、接口和测试，提醒可能的兼容性风险。不要直接把大范围重构当作阅读步骤。

验收：人可以逐行解释变更，运行相关测试与静态检查，并能说明尚未覆盖的情形。只有完成这些检查，才把补丁视为已掌握的代码。

## 五、可复用的 AI 提示模板

### 1. 来源约束的代码地图

```text
你是代码阅读助教。只依据我提供的文件、目录清单、测试和官方文档回答。
目标：解释 [具体阅读目标]。
请输出：
1. 入口和调用路径，每条附文件路径与行号。
2. 输入、关键状态、输出和外部副作用。
3. 事实、推断、待验证问题三张表。
4. 你认为最可能遗漏的两个分支，以及验证它们的具体命令。
没有证据的内容请写“待验证”，不要补全文件、接口或运行结果。
```

### 2. 苏格拉底式阅读

```text
请作为代码阅读教练，不要先给完整解释。
我会先回答问题。每轮只问一个与当前代码直接相关的问题，优先检查：
控制流、数据流、状态变化、异常路径、外部副作用。
等我回答后，再引用文件行号判断我的回答正确、遗漏或错误，并提出下一问。
如果代码证据不足，请说明需要查看哪个文件或运行哪个测试。
```

### 3. 执行预测检查

```text
基于以下代码和输入：[代码与输入]
请不要直接给最终输出。请先列出需要跟踪的变量、分支和调用。
给出一个可供我填写的状态追踪表，列为：步骤、代码位置、旧状态、条件、执行动作、新状态。
再提供一个边界输入和一个失败输入，并说明每个输入能区分哪些候选解释。
```

### 4. 对抗式审查

```text
这是我先写的理解：[人的解释]
请只做审查，不要重写成一篇新总结。
逐条检查我的陈述是否有代码、测试、日志或官方文档支持。
找出与我的解释冲突的路径、隐藏状态、默认值、异常和外部副作用。
把结果分为：已证实、证据不足、明确错误、需要运行验证。
```

### 5. 变更解释

```text
请审查下面的原始代码、变更 diff 和测试结果。
对每一处改动回答：
1. 它解决了哪个明确问题？
2. 它依赖哪些前置条件？
3. 删除它会破坏什么行为？
4. 哪个测试或运行观测支持它？
5. 哪些边界仍未覆盖？
如果无法从材料确认，请标为待验证，不要猜测作者意图。
```

## 六、人的掌握验收清单

以下是本报告提出的实践验收标准，属于跨来源归纳后的建议。对一个阅读单元，人在没有查看 AI 输出的情况下，应能完成：

1. 说明代码目标、输入契约、输出契约和外部副作用。
2. 画出一个正常输入的控制流和关键数据流。
3. 预测一个边界输入和一个失败输入的行为，并指出依据。
4. 说明关键状态的创建、更新、读取和释放位置。
5. 找到配置、依赖、接口和测试的来源。
6. 用源代码、运行结果或官方文档支持每个高风险结论。
7. 解释 AI 提出的至少一个候选假设为何成立或被排除。
8. 对每一处修改说明目的、保持的行为、影响范围和回滚方式。
9. 在测试通过后，再回答代码为何通过，以及测试没有覆盖什么。
10. 把未知问题、证据缺口和后续验证写入记录。

可以把掌握状态记录为：

| 状态 | 含义 |
| --- | --- |
| 已观察 | 代码、文档、日志或运行结果直接显示 |
| 已推断 | 多条证据支持，但仍依赖解释 |
| 已验证 | 通过测试、调试、静态分析或官方契约核对 |
| 待验证 | 已发现问题，缺少足够证据 |
| 已否定 | 经过反例或运行结果排除 |

## 七、容易削弱掌握的做法

1. 一开始就要求 AI 对整个代码库生成完整总结，再把总结当作地图。
2. 只看逐行解释，不查看调用方、测试、配置和运行状态。
3. 只用“测试通过”判断已经理解。
4. 让 AI 先写大补丁，再从 diff 中猜测设计意图。
5. 把代码中看起来熟悉的命名和模式直接当作正确含义。Wiedenbeck 的 beacon 研究提醒，强烈的表面线索可能带来错误理解。
6. 在探索模式下采用加速模式的快速接受标准。陌生 API、状态机、并发和副作用需要更长的检查与验证。
7. 让 AI 同时给出解释、结论和修改，导致人跳过预测、回忆和反例检查。

## 八、限制与待验证问题

1. 直接研究“AI 辅助大型生产代码库阅读，并长期测量人类掌握程度”的论文仍然较少。现有证据分散在程序理解、调试、代码教学和 LLM 用户研究中。
2. Barke 等人的研究有 20 名参与者，任务由研究者设计，重点为代码创作；Bexell 等人的大型代码库研究只有 5 名访谈对象。它们适合帮助设计流程，不能单独证明流程在所有团队有效。
3. 初学者研究显示了理解风险，但初学者的结果不能直接代表资深工程师。反过来，专业程序员在熟悉任务上的经验也不能推导出他们能掌握 AI 生成的大范围陌生代码。
4. 模型、IDE、上下文窗口和提示格式会变化。关于某个工具的效率或错误率，必须在具体版本与具体代码库中重新测量。
5. 解释质量受提示和学习者水平影响。2024 年关于 LLM 逐行代码解释的研究直接比较了不同提示、人工专家解释和不同掌握水平学习者，说明“能生成解释”与“解释适合当前学习者”需要分开评价。
6. 后续可以设计一个小型对照实验：同一代码阅读任务分为只看 AI 总结、AI 苏格拉底式提问、人工先解释后 AI 审查三组，统一使用无 AI 延迟回忆、反例预测、运行验证和变更解释作为结果指标。
